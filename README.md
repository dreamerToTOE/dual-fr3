# dual-fr3

This repository contains the **FR3-only** four-wall scene package for the
150 mm cube study. It is intentionally separate from the earlier episode
robot project and does not reuse its six-axis robot, runner, or validation
files.

The package describes:

- two Isaac Sim Franka FR3 robots;
- fixed L-shaped side-suction preview tools mounted at `fr3_link8`;
- the expanded four-wall geometry with a 150 mm cube and five target positions;
- two visual Y-axis rails using the current 1.5 m travel range.

Run the static preview inside Isaac Sim 4.5 with:

```bash
/home/ubuntu2004/isaacsim-4.5.0/python.sh fr3_four_wall_preview.py
```

The script writes `preview/fr3_four_wall_preview.usda` and two PNG captures.
The FR3 USD is resolved from the Isaac Sim asset root at runtime, so the
machine must have the official FR3 asset available.

## Base snapshots

The `base` history keeps two experiment states for the same 150 mm FR3 scene.
Commit `9a5dd79` is the no-cache environment snapshot. It contains the scene,
validation code, preview assets, and reports while the runtime planner creates
the A/B1/B2 paths online. It is the baseline for studying planning-time
behavior and online anomalies.

Commit `d2cf2d4` is the stored-trajectory environment. It adds the complete
120 Hz A/B1/B2 runtime cache, cache-first replay, state checks, and fallback to
the online RRT/IK planner. The current `base` branch points to this version,
while `9a5dd79` remains an ancestor in the same branch history.

`validation/fr3_b2_collision_plan.json` is the collision-constrained B2
preflight plan used by both states. The complete runtime cache generated by an
A/B1/B2 execution is stored separately in
`validation/fr3_trajectory_cache.json`.

## Independent Cube position comparison

The initial experiment's two separate streams are preserved in
`validation/idea_one_vision_comparison/`. Current runs put them under
`<output-dir>/vision/`: `ground_truth.jsonl` records the
Isaac Sim Cube position for reference, while `camera.jsonl` contains only
RGB/ArUco position observations (or an explicit missing observation).
`fr3_vision.py` receives an RGB frame, fixed camera intrinsics/extrinsics,
and known marker/Cube dimensions. It never receives a Cube ground-truth
position. The controller still uses its existing simulation state; this
experiment measures perception accuracy before connecting a fusion estimator.

Each camera observation uses its own rendering frame ID and exposure time.
The evaluator matches it to the 120 Hz reference history within half a
physics step. It records readout latency, excludes duplicate image frames,
and leaves missing detections empty instead of substituting ground truth.
Pose recovery uses the full PnP translation/rotation and marker-to-Cube offset.
The camera calibration is fixed before the run; no ground-truth bias fitting
is performed.

Run the automatic task, then generate the comparison plot and statistics:

```bash
/home/ubuntu2004/isaacsim-4.5.0/python.sh fr3_ab_visual_runner.py --close-on-finish
python3 fr3_vision_comparison.py validation/idea_one_b2_force_control/vision/comparison.jsonl
```

The directory also contains `metadata.json`, complete paired
`comparison.jsonl`, `comparison.csv`, `summary.json`, and `comparison.png`.
Statistics include XYZ bias/absolute error and 3D mean, median, RMSE, P95,
and maximum error, both overall and by task phase. Error statistics use
only valid time-matched detections; visibility/missing-frame counts remain
separate. The headless comparison is preserved independently in
`validation/idea_one_vision_comparison_headless/`.

The completed visible run had 906 matched detections out of 1,303 sampling
attempts (69.5%). Its 3D mean/RMSE/P95/maximum errors were respectively
24.8/29.9/56.5/134.8 mm. Stage mean errors were A 35.6 mm, B1 34.9 mm,
and B2 16.8 mm; the worst observation was during `B1_contact_transit`.
The mean signed XYZ errors were [+2.7, -12.5, -19.4] mm. All missing and
large-error observations are retained; no ground-truth correction or outlier
removal was applied. In visible mode, image readout lagged exposure by
16.7 ms; every matched reference used the exposure time (zero pairing delta).
Both headless and visible A/B1/B2 proxy-contact runs passed with 10,426
matching control/physics steps and zero uncommanded physics steps.

This is a comparison of simulated RGB sensing with PhysX ground truth.
The pinhole model has zero distortion; physical D455 calibration/noise and
fusion-based control are not validated by this comparison.

The recorded scene parameters are `cube_size_m=0.15`, Cube supply center
`[0.0,-0.3,0.787]`, back-wall target center `[0.0,1.076,0.787]`, B2 left-wall
target `[-0.245,1.076,0.787]`, wall inner bounds `x=±0.320`, right rail contact
`base_y=0.65`, FR3 bases `x=±0.44`, and a 1.5 m Y-axis rail. The machine-readable
snapshot is `validation/fr3_environment_snapshot.json`.

After a complete run, the runner stores the 120 Hz phase trajectories in
`validation/fr3_trajectory_cache.json`. The cache includes raw joint
waypoints, time-sampled joint commands, expected Cube centers, collision-check
reports, and rail base samples. Regenerate it with the automatic runner after
changing the scene configuration.

The runner loads a `COMPLETE` cache for the matching scene before each A/B1/B2
phase. It checks the measured joint start, TCP/Cube pose, and rail endpoints
before replay. A mismatch disables replay for the remaining phases and uses
the existing online RRT/IK planner. PhysX contacts, joint limits, Cube
deviation, and B2 dual-contact checks remain active during replay. A measured
collision or mid-phase deviation stops the run for inspection rather than
silently continuing.

This is a geometry preview only. It does not claim PhysX contact, suction,
ROS, IK, trajectory, or full B2 validation.

## Virtual six-axis wrist force feedback (idea-one, 2026-11-17)

Each arm now has an articulated fixed-joint sensor between `fr3_link8` and
the independent `ABSideTool` rigid body. The blue 12 mm sensor housing replaces
the first part of the original tool stem, retaining the TCP and the previous
conservative collision envelope. Every tool collider remains enabled. A's
temporary Cube attachment is connected to the tool body downstream of the
sensor, so the payload does not bypass the measurement.

Each virtual tool assembly has mass 0.3 kg, COM `[0, -0.06, 0.055]` m on the
left and `[0, 0.06, 0.055]` m on the right, and principal inertia
`[0.0015, 0.0007, 0.0012]` kg m². These are declared simulation parameters,
not a hardware calibration. They are stored in `wrist_force_sensors` in the
scene configuration and in each recording's `metadata.json`.

The 120 Hz recording reads actual PhysX incoming joint reactions in
`[Fx,Fy,Fz,Tx,Ty,Tz]` order (N and N m), not commanded gravity compensation
or controller efforts. The raw sign is parent-on-tool; the local frame and
origin coincide with the flange joint anchor. The residual is
`-raw_reaction - tool_gravity_wrench`, expressed both locally and in world
axes, with moments still referenced to the sensor origin. Tool inertia is
not removed. Cube truth and contact-pair identifiers are not sensor inputs;
phase names are evaluation context only. These are ideal physics signals
without added sensor noise, latency or saturation.

The first sensor-origin acceptance used `validation/idea_one_wrist_ft_visible/`
and `validation/idea_one_wrist_ft_headless/`; these historical directories are
preserved. Current commands and the TCP-origin extension are documented below.
Each run writes `runner_report.json`, `metadata.json`, `wrench.jsonl.gz`,
and a separate `trajectory_cache.json`; camera/reference streams are under
`vision/`. The analyzer produces `summary.json`, `wrench.png` and a B-only
`wrench_contact.png`. Saved nominal A/B1/B2 paths are still loaded from
`validation/fr3_trajectory_cache.json`, with the existing deviation/contact
guards. New runs do not overwrite that baseline cache or the earlier
`idea_one_vision_comparison` results. Use a fresh output directory to retain
multiple force-feedback runs.

The 28 actual PhysX load cases cover two sensor orientations, gravity,
all six positive/negative channels, and the moment of an offset force.
All passed, with maximum component errors `5.37e-7 N` and `2.92e-4 N m`;
the complete calibration record is `validation/idea_one_wrist_ft_load_check.json`.
The analyzer separately checks empty-tool residuals, the suspended bilateral
payload force against the configured Cube weight, B1/B2 pushing directions,
and the continuity of B2's left support force. A 1.5 s stationary window is
recorded after lifting and after crossing the front wall for this load check.

The complete visible acceptance is preserved in `validation/idea_one_wrist_ft_visible/`:
10,786 matching control/physics samples, zero uncommanded physics steps, and no
unexpected PhysX contact. Empty-tool residuals passed. Suspended combined
vertical forces were -12.2656 N after lift and -12.2615 N after crossing,
versus the configured -12.2625 N weight. B1 left median Fy was -0.9763 N;
B2 right median Fx was +0.7673 N in the central moving windows. All six
force/torque channels were finite throughout; the independent load check
validates their scale, sign, rotation and torque lever arm.

Sensor checks passed, but the force profile has task-level warnings:

- A transfer's opposing-force diagnostic peaked at 317.77 N while bilateral
  net force remained approximately `[0.019,0.064,-12.220]` N. This is consistent
  with internal loading of the two position-driven rigid attachment proxies;
  it is not evidence that a real suction connection would behave this way.
- B2 left median Fy was -0.3042 N, but only 58.6% of the evaluated moving
  window exceeded 0.1 N in the pressing direction: sustained preload is not
  established by the previous geometric hold check.
- Right and left withdrawal force peaks were 285.48 N and 122.75 N,
  respectively, during roughly the first 0.1 s of each withdrawal. The
  recorded TCPs initially moved slightly toward the Cube and PhysX still
  reported cup/Cube contact in these intervals. They are contact/control
  transients to investigate before claiming a normal-force baseline.

`summary.json` distinguishes sensor checks from these task warnings as
`PASS_FORCE_FEEDBACK_WITH_TASK_WARNINGS`. The release-peak screening rule
is relative to push forces; it is not a robot or sensor safety rating.
The earlier complete headless pilot in `idea_one_wrist_ft_headless/` retains
10,546 samples and its shorter 0.5 s suspended holds; those hold windows had
not fully settled and are honestly marked `UNVERIFIED` in that pilot summary.
The visible rerun uses the longer holds and passes both payload checks.
There are 51 passing unit tests, plus the 28 actual PhysX load cases and the
headless/visible complete task runs. The original `base` history is unchanged.

This sensor acceptance does not validate real suction or establish contact-state
classification. In particular, large opposing A loads can come from the two
rigid attachment proxies, and geometric B2 support proximity alone does not
prove sustained rear-wall preload. The measured limitations must be addressed
or explicitly excluded before treating these traces as normal training data.

## Sensor and TCP wrench feedback (idea-one, 2026-11-17)

Actual 120 Hz sampling now retains both reference points. The existing
`gravity_corrected_local/world` fields remain sensor-origin wrenches;
`tcp_gravity_corrected_local/world` are the corresponding TCP-origin wrenches.
Raw sensor reactions and the tool gravity wrench are still recorded. Both
origins use the same raw measurement, timestamp and physics step. Metadata
schema 2 records the origin and axes explicitly; older schema 1 logs remain
readable, with TCP verification marked `UNVERIFIED` rather than inferred.

The sensor-to-TCP displacement is taken from the same tool geometry as the
controller: left `[0,-0.155,0.08]` m, right `[0,+0.155,0.08]` m in sensor axes.
After removing tool gravity and its moment at the sensor, the sampling path
applies `F_TCP=F_sensor` and `tau_TCP=tau_sensor-r_sensor_to_TCP cross F_sensor`.
TCP local axes are parallel to the sensor axes; only the origin is translated.
Both wrenches also have world-axis versions, still referenced to their own
sensor/TCP origins, not to the world origin. `tcp_position_m` is calculated
from the same sensor pose and fixed offset, without Cube truth.

## B2 pressure hold and bilateral force release

Full historical B2 push evaluation gave only 50.1% left contact coverage and
a 1.4 s dropout; descent/approach had effectively no sustained preload.
Withdrawal commands also moved inward first: 0.861 mm on the right and
0.602 mm on the left, producing the measured 285/123 N peaks. The cause was
a duplicated-start Hermite spline tangent, reproduced exactly from saved
waypoints. Stationary segments now have zero tangents at both ends, preserving
intentional holds and their durations.

After B1, the left TCP rises by 4 mm, slowly seats the Cube against the rear
wall, then acquires a 2 N normal preload. Seating checks the rotated Cube
support radius against the known wall, allowing 20 um contact tolerance
and requiring force confirmation. This uses existing simulation state for
task control; it is not a fused state estimate or a sensor input.

The left arm tracks Cartesian X while retaining its acquired height and
orientation. Absolute world Y follows bounded force admittance:
`2e-5 m/(N s)`, 0.05 mm/s speed limit, 2 mm offset bound, 10 N overload stop.
It overrides nominal commands before every physics step, including right-arm
approach, rail movement and right release, without accumulating corrections
onto an already corrected path. B2 pushing uses a synchronized 15 s Cartesian
quintic with fixed orientations; the old joint-interpolated push is rejected.

Each arm ramps its normal target to zero, confirms less than 0.1 N for 30
consecutive steps, then retracts 35 mm straight outward over 3 s. The left
hold stays active until the right arm has retracted and Cube settling has
been checked. Measured forces are not clipped or replaced. Sensor/TCP
wrenches remain logged; `control.position_targets_rad` separately records
actually issued joint targets alongside measured joints.

Acceptance covers every declared hold sample, including stationary periods.
Coverage above 0.1 N and within 0.1--6 N must be at least 98%, with no dropout
longer than 0.05 s. All B2 phases, including acquisition/unloading, must stay
within 10 N total force and 1 N m TCP moment. Retreat must reach 30 mm with
at most 20 um inward excursion/backtracking. These are declared simulation
acceptance criteria, not hardware safety ratings; phase endpoints and spikes
are not discarded. Missing required phases fail validation.

The separate `validation/fr3_force_control_trajectory_cache.json` is preferred
only when controller revision, complete scene configuration, controller
parameters and recorded B2 force acceptance match. B2 additionally checks
its command/TCP start and endpoint before direct 120 Hz replay. A mismatch
rebuilds the contact path. Otherwise the legacy cache can supply the unchanged
prefix, while its old B2 push/withdrawal entries are explicitly invalidated.
Acquisition, force correction, unloading and withdrawal always run live.
The cache is nominal; actual corrected targets are in `wrench.jsonl.gz`.
The baseline cache and `base` history remain preserved.
